# Manufacturing Capacity & Ramp-up Optimization — Complete Case Package

**A reproducible, synthetic, Apple GSM-aligned manufacturing supply management portfolio project.** Not affiliated with Apple; no proprietary Apple data. Historical period: 16 weeks, Jan–Apr 2026.

## Quick start (no SQL Server required)

0. Read **`START_HERE_VI.md`** for the short Vietnamese learning guide.
1. Open **`outputs/dashboard.html`** in Chrome/Edge for the already-built interactive dashboard.
2. Open **`notebooks/Apple_GSM_Manufacturing_Case.ipynb`** in VS Code/Jupyter to see the **executed notebook with results**.
3. Read **`PROJECT_REPORT_VI.md`** for the Vietnamese business logic, actual KPIs, scenario interpretation, assumptions and caveats.
4. For SQL: use **`sql/01_sqlite_reproduce.sql`** with the included SQLite database or adapt **`sql/02_sqlserver_ssms.sql`** to your SQL Server cleaned/staging schemas.
5. For native Power BI: import the ready-to-use CSVs and follow **`powerbi/README_POWERBI.md`** and **`MEASURES.dax`**. This package contains an HTML dashboard but **not a `.pbix`** because Power BI Desktop is unavailable in this environment.

## Reproduce outputs in Python

Python 3.10+ recommended. From project root:

```bash
pip install -r requirements.txt
python python/run_project.py
python python/forward_plan.py
python python/stress_test.py
python python/build_dashboard.py
```

Stress testing is slower than the other scripts (150 scenarios × 4 policies, 600 LP solves). You do *not* need to rerun it to study the precomputed results.

## A note about data quality

The historical WIP ledger reconciles exactly to the snapshot. **Daily finished-goods snapshot fields appear inconsistent** (always zero) while opening FG + production - shipments reconstruct positive stock earlier in the period. This discrepancy is surfaced in the dashboard, not concealed.

## Why analyze 16 weeks that have already happened?

This is **historical diagnosis and counterfactual replay**, not an attempt to rewrite actual production. The historical period provides a controlled test bed for evaluating capacity bottlenecks and economic trade-offs; to make real decisions for the future, replace hindsight inputs with forecasts available at the decision date, implement rolling-horizon optimization and evaluate on held-out actual outcomes.

## Extra: forward-looking weeks 17–24 (addresses the “why change the past?” question)

The project also includes **`python/forward_plan.py`** and a **fourth dashboard tab**. It forecasts future W17–W24 demand using only W9–W16 observed demand (simple per-product linear trends), carries actual W16 inventories and backlog into W17, and tests additional machine/overtime policies with assumed 3-week purchase lead time. The forecast is deliberately labeled *illustrative*, not confirmed customer demand or a validated forecast.

Forecast future demand over 8 weeks ~607,573 units, plus opening backlog 7,816. The tested forward scenarios still fail to clear all demand (future F0 backlog at W24 ~195,382, F3 OT+Grinding ~134,091). Adding a Cutting machine on top of a Grinding machine does **not** improve performance under the model; Polishing becomes a projected 100%-load bottleneck at W24 when Grinding expands. This demonstrates bottleneck migration and why capex decisions must consider the entire production chain. **Do not use the forecast to approve real capital spending without validation.**

Run separately with `python python/forward_plan.py` after `run_project.py`.
